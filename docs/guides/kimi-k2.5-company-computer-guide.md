# Kimi K2.5 公司电脑落地指南

## 目标

这份指南解决的不是“如何让模型更聪明”，而是：

`如何在公司电脑只能使用 Kimi K2.5 的情况下，仍然稳定执行这套测试升级方法。`

核心原则是把自由发挥减少到最低，把输入、输出、步骤和边界都写死。

## 适用场景

这份指南适合以下场景：

1. 你在公司电脑上只能使用 `Kimi K2.5`
2. 你的真实工作代码仓库在公司电脑上
3. 你希望把当前这套测试升级方法迁移过去
4. 你不希望依赖模型的长链路推理能力

## 总原则

在 `Kimi K2.5` 上，不要让模型“自己想整个方案”，而要让它：

1. 只处理一个明确目标
2. 只看必要上下文
3. 只输出固定格式
4. 不允许擅自扩范围
5. 优先给出最小答案，不给大而全答案

一句话总结：

`把模型当成严格按模板执行的助手，不当成自由发挥的顾问。`

## 提问前准备

每次在公司电脑上提问前，先自己准备这 4 类信息。

### 1. 改动范围

只告诉它本次真正相关的文件或类，例如：

1. `OrderService.java`
2. `OrderController.java`
3. `PaymentCallbackHandler.java`

不要把整个项目都丢进去。

### 2. 当前目标

每次只选一个：

1. 帮我找最值得补的 1 个测试
2. 帮我把一个 bug 变成回归测试
3. 帮我教我看懂一个最小单元测试
4. 帮我列一次最小发版检查

不要把多个目标混在一个提问里。

### 3. 约束

必须明确告诉它：

1. 当前技术栈
2. 当前只能接受多大改动
3. 不能扩展到哪些范围

例如：

```text
技术栈：Java8 + Maven
目标：只补 1 个最小单元测试
限制：不要改其他模块，不要设计完整测试体系，不要输出超过 3 个测试建议
```

### 4. 你期望的输出格式

必须写死输出结构，例如：

```text
请只输出 3 部分：
1. 最值得测的一个场景
2. 对应的测试代码骨架
3. 运行命令
```

## 适合 Kimi 的提问规则

### 规则 1：一次只问一件事

正确：

`请帮我从这个 service 改动里选 1 个最值得补的单元测试。`

错误：

`请帮我分析风险、设计测试体系、补单元测试、补接口测试、顺便给我出回归方案。`

### 规则 2：一定要限制输出范围

正确：

`最多给 2 个测试建议，并说明你更推荐哪一个。`

错误：

`请尽可能全面地帮我设计。`

### 规则 3：一定要限制改动范围

正确：

`只基于下面这个类输出建议，不要扩展到其他模块。`

错误：

`你看着办。`

### 规则 4：一定要要求固定结构

如果不固定结构，低能力模型很容易：

1. 讲很多道理
2. 给不出最小答案
3. 擅自扩展任务

所以尽量用：

1. `请只输出 3 部分`
2. `每部分不超过 5 行`
3. `如果信息不足，先列缺失信息，不要猜`

### 规则 5：优先让它生成骨架，不要让它一次性生成完整方案

正确：

`请生成最小可运行 JUnit 测试骨架。`

错误：

`请生成完整测试体系和所有测试代码。`

## 三种高频工作流

### 工作流 1：改高风险后端逻辑时

目标：

`让 Kimi 帮你判断本次最值得补的 1 个测试。`

你给它的输入应该包括：

1. 本次改动的类或方法
2. 这次改动的业务意图
3. 历史上这里是否出过 bug

它的输出应该被限制为：

1. 一个最高风险点
2. 一个最小自动化测试建议
3. 一个最小手工验证动作

### 工作流 2：修线上 bug 之后

目标：

`让 Kimi 帮你把这次 bug 变成最小回归测试。`

你给它的输入应该包括：

1. bug 现象
2. 根因
3. 修复代码

它的输出应该被限制为：

1. bug 假设
2. 最小复现测试
3. 最小断言

### 工作流 3：你还不会写测试时

目标：

`让 Kimi 先教你看懂并补出 1 个最小后端单元测试。`

你给它的输入应该包括：

1. 一个真实的 Java 方法
2. 方法依赖了什么
3. 你当前卡在哪里

它的输出应该被限制为：

1. 为什么这个方法值得先测
2. 测试结构拆解
3. 最小代码骨架
4. 运行命令

## 推荐的固定使用方式

在公司电脑上，建议你固定成下面的节奏：

1. 改代码前，用高风险改动模板问一次
2. 修 bug 后，用 bug 转回归测试模板问一次
3. 每周一次，用周回顾模板更新风险清单和测试债务
4. 学测试时，只拿一个真实 Java 方法练一次最小单测

## 不要这样问

以下是低能力模型场景下最容易失控的提问方式：

1. `帮我把这个项目的测试体系都搭好`
2. `帮我看看哪里都可能有问题`
3. `请尽可能全面分析`
4. `顺便再帮我补接口测试和前端测试`
5. `你自己判断还需要做什么`

这些问法会导致输出：

1. 过长
2. 不聚焦
3. 难执行
4. 很容易偏离你当前目标

## 推荐的成功标准

在公司电脑上，不要先追求“模型回答很惊艳”，而要追求这几个结果：

1. 它能稳定给出一个可执行的最小测试建议
2. 它不会频繁乱扩需求
3. 你可以重复套用相同模板
4. 你能在 10 分钟内从提问走到开始动手

## 最后原则

如果你发现 `Kimi K2.5` 经常答偏，不要先怀疑方法本身，先检查这 3 件事：

1. 你是不是一次给了太多上下文
2. 你是不是一次问了太多问题
3. 你是不是没有把输出格式限制死

只要这三件事控制住，低能力模型也可以稳定服务这套流程。
