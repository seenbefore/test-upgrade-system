# 从不会测试到可持续测试的渐进式方案设计

## 1. 背景

用户是 `Vue2 + Java8` 的全栈开发工程师，当前长期加班，目标是获得更多可支配时间。

当前问题链路已经明确：

1. 人员不足、排期紧张
2. 测试能力缺失，当前主要依赖手工点页面验证
3. 上线后后端问题更常见
4. 线上 bug 导致返工、救火、上下文切换和额外加班

这里的核心事实不是单纯“缺少测试体系”，而是：

`用户目前既缺测试时间，也缺测试方法和测试实战经验。`

因此，本设计不采用“一步到位建设完整测试体系”的路线，而是采用：

`先建立最小测试能力，再建立轻量测试闭环，最后逐步进化为完整体系。`

## 2. 设计目标

本方案有两个并行目标：

1. 让用户先学会最小可用的测试能力
2. 用这项能力逐步减少线上 bug、返工和加班

更具体地说，方案需要满足以下要求：

1. 通用，可迁移到大多数 `Java8` 后端业务场景
2. 可执行，能嵌入紧张排期下的真实工作
3. 轻负担，不能把“学测试”本身变成新的重压
4. 有发展潜力，后续可以自然演进到完整测试体系
5. 适合由 `Cursor Agent` 长期辅助维护

## 3. 非目标

以下内容不作为当前阶段的目标：

1. 一次性补齐历史代码的测试
2. 立刻建设完整的单测、集成测试、端到端测试和 CI 门禁体系
3. 覆盖所有前端和后端模块
4. 推动整支团队立刻改变流程
5. 追求测试覆盖率数字本身

当前阶段只追求：

`用最小投入建立最小能力，并优先拦住最容易导致加班的后端线上问题。`

## 4. 约束

当前已知约束如下：

1. 时间少，长期加班，无法腾出整块时间系统学习
2. 推动空间有限，难以直接推动团队级流程升级
3. 当前几乎没有自动化测试基础
4. 用户没有单元测试、集成测试、端到端测试的实战经验
5. 后端线上问题比前端更多，因此优先级更高

这些约束决定了方案必须满足：

1. 每次只要求学习一个很小的测试动作
2. 每次只要求补一个最关键的测试点
3. 学习必须绑定真实需求、真实 bug 和真实改动

## 5. 备选路线与取舍

### 路线 A：完整测试体系优先

做法：

1. 系统学习测试理论
2. 搭建单测、集成测试、接口测试、回归测试
3. 最终接入 CI 和发版门禁

优点：

1. 长期最完整
2. 体系性最好

缺点：

1. 启动成本高
2. 对当前时间和精力要求过高
3. 容易因为无法落地而中断

### 路线 B：关键后端兜底优先

做法：

1. 只关注后端高风险逻辑
2. 结合真实 bug 和真实改动逐步补最小测试
3. 用最轻的方式建立风险清单和回归清单

优点：

1. 与当前问题最贴近
2. 最容易尽快减少线上事故
3. 最适合高压环境下启动

缺点：

1. 前期覆盖不完整
2. 需要接受“先救最痛的 20%”而不是全面完善

### 路线 C：先靠人工流程防呆

做法：

1. 建发版 checklist
2. 固定手工回归模板
3. 通过流程减少事故

优点：

1. 立刻可开始
2. 几乎零门槛

缺点：

1. 仍然主要依赖人
2. 难以真正减少长期负担
3. 无法自然进化出测试能力

### 结论

选择 `路线 B + 少量路线 C`，并在路线 B 前补一个“测试能力入门阶段”。

## 6. 选定方案

最终选择的方案是：

`让 Cursor 带着用户，用真实工作中的后端 bug 和高风险逻辑，边做边学最小测试能力；学会后，再把这些零散动作沉淀成轻量测试闭环；最后逐步演进到完整测试体系。`

这是一个四阶段模型。

## 7. 四阶段演进模型

### 阶段 0：入门脱盲

目标：

1. 先理解测试的基本概念
2. 学会写最小可运行测试
3. 不追求完整，只追求“能开始”

本阶段只学习：

1. 什么是单元测试
2. 什么是集成测试
3. 什么是端到端测试
4. 当前阶段为什么优先后端单元测试
5. 一个最小测试由什么组成
6. 如何写输入、执行、断言

本阶段不学习：

1. 大而全的测试理论
2. 复杂测试框架高级特性
3. 大规模 Mock 技巧
4. 端到端自动化测试体系建设

设计原则：

`先会写一个，再谈写得多。`

补充说明：

1. 阶段 0 的唯一动手目标，是先写出第一个最小后端单元测试
2. 集成测试和端到端测试此阶段只建立概念认识，不作为立即实操目标

### 阶段 1：跟着真实工作学

目标：

1. 不脱离业务上下文学测试
2. 每次只练一个最小动作
3. 每次都和真实需求或真实 bug 绑定

优先练习的动作：

1. 给一个 Java 业务方法补 1 个单元测试
2. 给一个线上 bug 补 1 个复现测试
3. 给一个高风险分支补 1 个边界 case
4. 在已经能写最小单元测试之后，再给一个关键接口补 1 个最小接口级验证

设计原则：

`不单独学测试，而是在解决当前工作问题时顺手学测试。`

这里的“最小接口级验证”指：

1. 优先是后端内的轻量接口验证，例如基于现有后端测试框架对接口输入输出做最小检查
2. 如果当前项目或能力条件还不支持自动化接口验证，则先用结构化手工验证或固定 Postman 检查项过渡
3. 它的优先级低于“能写最小后端单元测试”

### 阶段 2：形成轻量闭环

当用户已经能写最小测试后，开始固化为固定动作：

1. 维护风险清单
2. 高风险改动至少补 1 个测试
3. 修 bug 时补复现测试
4. 发版前执行最小回归清单

设计原则：

`不求完整闭环，但求每次上线都比上一次更稳一点。`

进入阶段 2 的建议条件：

1. 已经能在 Cursor 辅助下独立补出最小后端单元测试
2. 已经至少完成 `2-3` 次“修 bug 或改高风险逻辑时顺手补 1 个测试”
3. 已经开始能分辨哪些逻辑适合先用单元测试兜底

### 阶段 3：逐步体系化

当测试资产和习惯积累到一定程度后，再逐步演进：

1. 从业务层单测扩到少量接口测试
2. 再扩到关键业务链路集成测试
3. 逐步接入自动化执行和门禁
4. 最终进入完整测试体系建设

设计原则：

`前面的投入不能推倒重来，而是能自然长成完整体系。`

## 8. 当前最优先的测试范围

在所有测试类型里，当前优先级如下：

1. `Java8` 后端业务层单元测试
2. 少量关键接口验证
3. 发版前最小人工回归
4. 前端自动化测试暂缓
5. 复杂端到端自动化测试暂缓

之所以暂缓前端自动化，不是因为前端不重要，而是因为当前问题链路里：

1. 后端线上问题更多
2. 后端单元测试的学习和落地成本更低
3. 更容易先把返工和救火压下来

优先测试的业务点包括：

1. 状态流转
2. 权限判断
3. 金额或核心数据计算
4. 去重、防重复提交
5. 参数校验和异常分支
6. 历史线上事故对应逻辑

优先级排序规则只有三条：

1. 经常改
2. 出过线上事故
3. 一旦出错影响大

## 9. 轻负担执行机制

方案的最小执行闭环如下：

### 9.1 风险清单

只维护一个小清单，通常 `5-10` 项即可。

每项只记录：

1. 模块或接口名
2. 出过什么问题
3. 下次改这里必须验证什么

它的作用是帮助快速判断：

`这次改动是否碰到了高风险区域。`

### 9.2 补测规则

固定规则为：

`以后凡是改到高风险后端逻辑，就至少补 1 个能拦住这次问题的自动化测试。`

这条规则刻意保持轻量，原因是：

1. 不要求补历史债
2. 不要求每次写一堆测试
3. 能随着真实改动持续积累

### 9.3 bug 复现测试

固定规则为：

`线上 bug 修掉后，尽量补 1 个最小复现测试，避免同一个坑反复出现。`

它是整个方案里收益最高的动作之一，因为它直接把事故经验沉淀成资产。

### 9.4 发版前最小回归

在自动化还不完整前，保留一份最小回归模板，只检查：

1. 本次改动直接影响的核心接口
2. 历史最容易出问题的 `1-2` 条业务链路
3. 最关键的异常分支

这不是为了追求覆盖完整，而是为了减少发版前临场思考成本。

### 9.5 测试债务清单

测试债务清单是风险清单的补充，不是另一套重流程。

两者关系如下：

1. 风险清单记录“哪里容易出事、下次改动必须注意什么”
2. 测试债务清单记录“已经知道应该补，但这次来不及补的测试项”

测试债务清单每项只记录：

1. 对应模块或接口
2. 为什么应该补
3. 建议补哪一种最小测试
4. 当前未补的原因

维护原则：

1. 只有在“本次明确识别出价值，但来不及补”的情况下才新增
2. 数量应尽量小，优先保留高风险项
3. 每周可由 Cursor 协助整理一次，避免堆成新的负担

## 10. Cursor Agent 的职责设计

Cursor 在本方案中不是单纯的“代码生成器”，而是四类角色的组合。

### 10.1 测试教练

作用：

1. 基于当前真实代码解释应该写哪种测试
2. 告诉用户为什么这样测
3. 用最小示例帮助用户理解测试结构

适用阶段：

1. 阶段 0
2. 阶段 1

### 10.2 样板生成器

作用：

1. 生成最小可运行单测骨架
2. 生成测试数据样板
3. 生成最简单的 Mock 或依赖替身写法

适用阶段：

1. 阶段 0
2. 阶段 1
3. 阶段 2

### 10.3 维护员

作用：

1. 维护风险清单
2. 维护测试债务清单
3. 维护历史 bug 对应测试项
4. 维护最小回归清单

适用阶段：

1. 阶段 2
2. 阶段 3

### 10.4 发布前检查助手

作用：

1. 基于本次改动范围，列出最小回归建议
2. 提醒高风险验证点
3. 帮助减少遗漏

适用阶段：

1. 阶段 1
2. 阶段 2
3. 阶段 3

## 11. 人与 Cursor 的分工边界

用户负责：

1. 判断业务优先级
2. 判断哪个模块最值得先补
3. 审核测试是否真的有价值
4. 选择当前能承受的投入强度

Cursor 负责：

1. 分析改动风险
2. 推荐最小测试点
3. 生成样板和草稿
4. 沉淀可复用资产
5. 维护清单和记录

设计边界如下：

`人做业务判断，Cursor 做维护和加速。`

## 12. 忙碌场景下的容错设计

这个方案必须在“很忙的时候也不至于完全断掉”。

因此需要明确最低保底动作：

### 情况 1：没时间写完整测试

最低动作：

1. 补 1 个最关键 case

原则：

`宁可少写，也不要完全跳过。`

### 情况 2：需求太赶，来不及整理

最低动作：

1. 把这次风险记录进清单
2. 发版前走最小回归

### 情况 3：团队不支持体系化表述

建议话术：

`先给几个高风险点加最小校验，减少线上返工。`

这样比“建设测试体系”更容易获得接受。

### 情况 4：测试写得越来越重

说明当前粒度可能过大，应退回去优先测试：

1. 业务规则本身
2. 关键分支
3. 明确输入输出

而不是一开始就测整条复杂链路。

## 13. 演进路径

本方案的成长路径如下：

1. 先会写最小测试
2. 再把测试绑定到真实 bug 和高风险逻辑
3. 再沉淀模板、清单和习惯
4. 再扩展到更广的接口和链路
5. 最终接入自动化流程和门禁

它最终会从：

`不会测试 -> 会写最小测试 -> 能持续补关键测试 -> 能维护轻量闭环 -> 能建设完整体系`

逐步进化。

## 14. 成功标志

判断方案是否有效，不看覆盖率数字，优先看这些信号：

1. 用户已经能独立补出最小后端单元测试
2. 修 bug 时开始形成“修复 + 补测试”的习惯
3. 高风险模块开始有可复用测试资产
4. 发版前需要临场思考的内容减少
5. 后端重复性线上 bug 开始下降
6. 晚间返工和救火频率下降

## 15. 下一阶段建议

本设计通过后，下一阶段不应直接进入编码，而应进入实施计划设计，重点回答：

1. 第一周先学什么，不学什么
2. 第一个月如何用真实工作练最小测试能力
3. Cursor 的固定使用方式如何落地
4. 风险清单、测试债务、回归清单分别用什么文件维护
5. 如何把“不会测试”分解成最小学习路径

## 16. 最终结论

本设计的最终结论是：

`对当前用户而言，最优方案不是直接建设完整测试体系，而是让 Cursor 带着用户，在真实工作中以最小成本学会最小测试能力，再把这些能力沉淀成轻量测试闭环，并逐步演进到完整体系。`

这是一个兼顾现实约束、学习曲线、减压目标和长期发展潜力的方案。
